{%- endmacro -%} {#- ===================== 未纳入的组件（实测结论，2026-09-10）===================== V2 原计划还包含 button / card / modal / field / badge_state / stat。实测后**未采纳**， 理由是它们不满足"结构重复且统一"这个前提，硬做成宏会变成过度抽象： - **card（17 处）**：骨架并不统一——有的 header 只放标题、有的带右侧操作区、 有的是 `
/` 可折叠、login 里甚至只是 Tab 切换容器。 要覆盖这些差异就得给宏加一堆可选参数，等于把复杂度从标记搬到参数，得不偿失。 若要抽，只值得抽其中的 `
` 标题元素 —— 但那是"只差一个 class"，收益不足以支付一层间接。 - **modal（11 处）**：外壳（遮罩 + 背景层 + 内容盒）确实统一，但**属性不一致**—— 部分带 `tabindex="-1"`、部分没带，且 `aria-labelledby` 目标各不相同。 统一它们会**改变输出**（属 a11y 归一化，是 V3 的范围，因为 V3 本来就要动标记）。 → V3 待办：把 11 处模态外壳统一为带 `role="dialog" aria-modal="true" tabindex="-1"` 的一致形态，并顺手确认每个模态的初始焦点与 Esc 行为。 - **badge_state（表层 ~100 处）**：实测发现这些高亮类绝大多数不是"状态徽标"， 而是代码 chip（`font-mono text-xs bg-zinc-100 dark:bg-zinc-700 rounded px-1`）、 提示条、告警条等，语义与配色规则各不相同，不存在一张统一的状态→色映射表。 → V3 待办：先把"签到状态"这一族真正的状态徽标挑出来，再按语义定色。 - **button / field（btn-* / input 等）**：已经有了 CSS 类这一层抽象 （`.btn-primary` / `.btn-ghost` / `.yb-input`），再包一层宏只是多一跳，不增加信息。 - **stat**：目前只有时钟一处用到，尚未形成重复。 结论：**先只抽真正重复且统一的那一类**（空态）。等 V3 把视觉系统落地时， 若某类组件在替换过程中确实形成了稳定形态，再补进本文件 —— 那时它有真实的第二个使用场景， 而不是凭猜测先建。 -#}
