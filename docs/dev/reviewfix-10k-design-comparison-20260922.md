- **A（本文档所指"对手方案"）**：`D:\Documents\QQ\yiban-10k-scheduler-design.md`（下称 A 案）
- **B（我方方案）**：`docs/dev/reviewfix-10k-algorithm-20260922.md`（下称 B 案）

> 结论先行：**A 案在"并发模型 / 状态统一 / 分工确定性 / 库读写隔离 / 自适应体系"五处优于 B 案，应并入；
> B 案在"耐久性分级 / 聚合速率不变量 / gap 是否可删 / 契约迁移显式化 / 证据来源"五处对 A 案构成实质修正。**

## 1. 两案共识（不必再争的部分）

1. **核心瓶颈不在 SQLite，在"执行体内串行排队"**：A 案 §1.2 与 B 案 §0 结论一致
   （B 案从"`周期 = t + gap`"切入，A 案从"`sleep(gap)` 串行循环"切入，同一件事）。
2. **计划必须确定性、可重放**：`hash(phone, day)` 进种子；两案一致（A 案 §3.2，B 案 §2②）。
3. **领取要批量化**，不能每次尝试一次单行 upsert：A 案 §5.2（32 行/事务）、B 案 §6.2（批量提交）。
4. **短租约 + reaper 替代 900s 长租约**：A 案 §4.3（任务级 60s）、B 案 §4（退避 + 终态收敛）。
5. **状态文件必须退出热路径**（迁库 + 异步物化保读侧契约）：A 案 §5.4、B 案 §6.1。
6. **出口级令牌桶 + AIMD**：A 案 §6.2、B 案 §5（且都主张以**风控信号**而非延迟作回退信号）。
7. **不引入 Redis/MQ/Postgres/共识协议**：A 案 §11.4、B 案 §10.3。
8. **容量公式必须同步改**（web 保存闸门 `_capacity_estimate` 的串行口径会被新模型碾压）：两案都提，
   但 **A 案更狠也更准**（见 §2 第 9 项）。

## 2. 分歧逐项对比

| # | 议题 | A 案（对手） | B 案（我方） | 判定与依据 |
|---|---|---|---|---|
| 1 | **单执行体并发模型** | **asyncio × M 并发通道**（M 按出口桶自动），`sleep_until` 精确到点；单进程内多通道并行 | 保持**进程即并发单位**（一进程同时只跑一个账号），靠 K 个进程提供并发 | **A 更优**。40 号实测"单账号 90% 是网络等待、最大并发=1（证实串行）"——把等待变成并发是唯一能提高**每出口 IP**吞吐的手段。B 案的 K 只增加"出口数"，不增加"每出口并发"。→ **应并入 A**（但注意 A 自己也标注了 client 需同步→异步的改造风险 §10.1） |
| 2 | **状态与队列的表结构** | **一张 `sign_tasks`**（vshard/owner/run_at/priority/state/attempts/lease_until），**把 `sign_claims` 并入** | 保留 `sign_claims`，**另加** `sign_state` 表放每账号状态 | **A 更优**。B 案会造成"claim 表 + state 表"两份互相冗余的状态源（谁回答"当日是否了结"变成两处口径）。A 案合并后单表回答，且 `attempts` 跨执行体共享（顺带修掉"重试预算存在内存里、A 失败 2 次被 B 接手就重置"的真实缺陷）。→ **应并入 A** |
| 3 | **分工方式** | **HRW + 256 虚拟分片**：确定性 owner、日常零竞争、按分片索引批量领取；心跳过期才按分片整体窃取 | **共享池 + 竞争领取**：不实现 HRW/P2C/窃取（理由：共享池已免费提供分配，且速率上限必须集中） | **A 在写路径上更优**（无竞争 + 按 `vshard` 索引批取）；B 在"K 变化时计划不作废"上更优。但 B 案的核心论据（"集中式分发多一层转发"）针对的是 **Director**，而 A 案的 HRW 是**无中心纯函数**，不构成额外转发——**B 案这条否决理由对 A 案不成立，应当撤回**。→ **应并入 A**（保留 B 案"计划是纯函数"的性质：owner 与 run_at 都由哈希决定，落库只是可查询视图） |
| 4 | **计划是否落库** | **落库**（`sign_tasks`，v18 迁移 + 灰度开关） | **不落库**（纯函数按需派生，工作集从状态派生） | **两案可合**：A 案的落库换来"可查询/可审计/崩溃不漂移/兜底共享待办视图"；B 案的纯函数性质可同时保留（落库值 = 函数值，重算用于校验与自愈）。B 案反对落库的真正理由（避免状态）在 A 案里被"单表统一状态"抵消。→ **采纳 A 的落库，但把"函数即真相、表即视图"写成不变量**（表被损坏可重算恢复） |
| 5 | **耐久性 `synchronous`** | queue.db / events.db 用 **`NORMAL`**，理由"掉电丢最后一批，重试可补" | **分级**：claim/settle（决定"是否已登录"）用 **`FULL`**，事件行用 `NORMAL` | **B 案对 A 案构成硬修正**。SQLite 官方 pragma 文档：WAL+`NORMAL` 会丢**最近提交**（断电可能回滚）。而 `sign_tasks` 现在**就是**回答"是否已登录"的那张表 ⇒ 回滚后账号显示 pending ⇒ **再登录一次 = 重复真实登录**，正是本项目的红线。**A 案"重试可补"的推理对终态不成立**（对已登录账号，"重试"就是再登一次）。→ **A 案必须改**（写入量 11–13 行/s，FULL 有 40× 余量，付得起） |
| 6 | **账号间隔 gap** | 列为"落后设计"，由出口令牌桶 + AIMD 取代（`gap`/`min_exec_gap` 收口进桶参数） | **保留每账号 GCRA**（`T=gap, τ≈0`），与全局令牌并存 | **需实测裁决，不能单方面删**。仓库 `43` 号 §7 明确把"账号间隔 gap"列为**必保项**（"账号间隔 gap、幂等、到期兜底三个底限在两种形态下都不可移除"）；`43` §4.2④ 还指出"若跨账号最小间隔是**全局硬约束**，容量≈`W/gap`，加执行器无效"。删 gap 的前提是**证明上游不按账号维度看间隔**——这条**两案都还没验**（B 案把它列为阻塞性未知）。→ **合并方案：保留 gap 作为可选安全件，由实测决定默认开关** |
| 7 | **速率上限的语义** | 每出口一个桶（K 出口 ⇒ 聚合 = K × bucket），**扩容首先是加出口** | 把"聚合请求速率"作为**一等公民**，要求 `≤ min(φ, Λ)` **且与 K 无关** | **A 更贴合现实**（风控大概率按出口/IP 计数，所以每出口桶是对的）；**B 的不变量仍然有用**（它防止"加进程就自动放大总速率"这一误操作，并可表达"平台总容忍度"这一上界）。→ **合并：每出口桶（A）+ 总速率上界 Λ（B）双层**；当 Λ 存在时，**加出口不再线性放大总速率**——这一条要写进运维文档，否则运维会用"加进程"来解吞吐问题 |
| 8 | **风控整形（分布形状）** | **弃用正态钟形**，改**分层抖动**（`slice = i mod N_slices` + 哈希选微槽 + 相位），理由"钟形是固定指纹、熵低"；并承认小 N 会前载 | **保留三种模式**（sequence/random/normal 是**产品可选项** `YIBAN_SIGN_ORDER/SIGN_DIST`），但新增 `φ_max × N ≤ Λ` 约束削峰；采样用 NHPP 反演 | **A 的"形状=指纹"是合理假设但未验证**；且 A 案**静默取消了产品既有开关**（`SIGN_DIST=normal` 是用户在设置页能选的），属产品变更而非纯引擎优化——**必须显式提出来让用户拍**。B 案保留开关但补了峰值约束。→ **合并：保留三模式（产品契约），在引擎侧用分层抖动实现"均匀"模式、用受速率约束的密度实现"正态"** |
| 9 | **保存闸门容量公式** | **明确列为同日必改**：`_capacity_estimate` 串行口径上限 ≈323，新模型下 >323 账号的站点**保存设置必被误拒**，且"1k 正常体量下已经触发，是今天就存在的隐患" | 未提及 | **A 案更优，且抓到一个今天就在的隐患**。B 案应在 §6 补此条（并注意它与本项目记忆里"容量口径统一：可容纳账号数由 260 上调为 360"是同一处） |

| 11 | **补签轮 / 退出码契约** | **明示保留**："`--only` 手动签到、补签轮、退出码契约（0/1/2/3/10）逐字保留" | **主张退场**：连续工作集吸收其职责，并**显式列出要迁移的三个契约**（`need_second_run`、退出码 10、`_is_second_run`）+ **发布门禁"有效轮次"定义需重新商量** | **A 更保守、风险更低；B 更彻底但引入治理性变更**。注意：在 A 案里保留补签轮**几乎零成本**（持久化队列下"再跑一遍消费者"而已）。而 B 案点出的"发布门禁定义"是真实牵连——**该议题不能只由技术方案单方面决定**。→ **合并：技术上保留补签轮作为"再消费一遍队列"（低成本、零新契约），把"取消它"作为独立治理项另议** |

## 3. A 案需要订正的两处（可证伪的具体点）

**① "req/s" 的单位与请求量核算差 6 倍**
A 案 §6.2 写"令牌桶（每出口）：`rate = 1 req/s`"，§11.1 又写"单执行体有效速率 1/s（桶限制）"、
"5k 档出口 IP 请求量 **3,000/IP**（K=2）"。但本项目**单账号 = 6 次 HTTP 请求**（登录链 4 + 定位 + 签到）。
按"1 次尝试/s ≈ 6 次请求/s"理解，则 3,000 次尝试/IP = **18,000 次请求/IP/窗口**（≈4.3 req/s 持续），
而 A 案 §11.2 却据此判断"每 IP 一窗口 3,000 次请求已接近风控敏感区"——**风险评估可能低估 6 倍**。
⇒ 需明确：桶是按**请求**还是按**账号尝试**计；若是前者，K 与吞吐的分档表要整体重算。

**② 跨 WAL 库的原子提交（已由官方文档证实）**
SQLite 官方 WAL 文档在"drawbacks of WAL"里明确写道：跨多个 attached 数据库的事务
**"are atomic for each individual database, but are not atomic across all databases as a set."**
（<https://sqlite.org/wal.html>，2026-09-22 实取）
⇒ A 案的三库若都用 WAL，"claim 写入"与"事件/审计写入"分属两库时**不能放在同一事务里**。
虽然 A 案自己写了"热路径独占，无跨库 join"，但**必须显式声明"不假设跨库原子性"**，
并在设计上改为"幂等 + 补偿"（例如：先写 queue.db 的终态，再异步补 events.db；
中间崩溃由 reaper/补偿扫描兜住，而不是靠同一事务）。

## 4. B 案需要撤回/修正的两处（我自己的）

**① 撤回"不实现 HRW/虚分片"的否决理由。**
B 案当时的论证是"共享池已免费提供分配 + 速率上限必须集中"，并据此否决 Director+HRW+P2C+偷取。
但 A 案的 HRW 是**无中心纯函数**（`argmax H(phone‖day‖executor)`），不引入转发层，
而且换来"日常零竞争 + 按 `vshard` 索引批取 + 分片级租约接管"——**B 案的否决理由只对 Director 成立，对 HRW 不成立**。
（B 案的正面对手是"集中式分发"，A 案恰好也没用集中式分发。）

**② 补两条 A 案有、B 案缺的具体项**：保存闸门容量公式（§2 第 9）、按 vshard 分片解密（§2 第 10）。

## 5. 合并后的最佳形态（取两案之长）

```
计划层：Planner（每日一次）
  · 落点 = hash(phone, day, 分层抖动)  ← A 的分层抖动（方差最优、弃固定钟形指纹）
  · owner = HRW(phone, day) + 256 虚分片  ← A 的确定性分工
  · 落库 sign_tasks（单表统一：计划 + claim + state + attempts + 租约）  ← A
  · 但保留 B 的不变量：表是函数的视图，可从 (phone, day) 重算恢复

执行层：每执行体 = asyncio × M 通道（M 按出口桶自动）  ← A
  · 批量领取 32 行/事务（按 vshard 索引，天然不相交）  ← A
  · 每出口令牌桶 + AIMD（风控信号回退、桶状态落库）  ← A
  · 事件/心跳/settle 写合并  ← A
  · 分层耐久性：claim/settle 用 FULL，事件用 NORMAL  ← B（对 A 的硬修正）
  · 每账号 GCRA(T=gap) 作为可选安全件（由实测决定默认）  ← B（与 43 号"必保项"一致）

收敛层：退避（decorrelated jitter，A）+ 落点有界于 deadline（B）+ attempts 跨进程共享（A）
       + 近截止 hedged（B，靠 already 幂等）+ 分片级心跳/租约接管（A）
       + 终态单写 + fencing epoch 覆盖**所有**终态写（B）
       + 补签轮保留为"再消费一遍队列"（A，低成本），取消它另作治理项（B 的提醒）

存储层：三库分离（A）+ 读连接 query_only（A）+ 不假设跨库原子性（B 的订正）
       + 状态文件退出热路径、异步物化保读侧契约（两案一致）

参数层：A 案 §12 的四类自适应体系整体采纳（含"安全类永不自适应"、人工优先）
       + B 案保留：延迟信号在近常量服务时间下要保守；标定值作种子而非让在线学习从零开始

证据层：保留 B 案的官方源纪律（SQLite pragma / Postgres 文档 / Kleppmann fencing / Netflix·Envoy 官方）
```

**一句话**：A 案是更完整、更工程化的**架构**；B 案是更严谨的**约束与证据**（耐久性、聚合速率不变量、
fencing 覆盖面、契约迁移的牵连）。**合并后**，架构取 A、约束与证据取 B，两案各自的"自我修正"都保留
（A 的 2.3× 高估与固定 M/K、B 的 HRW 否决理由与缺失的两条具体项）。

## 6. 仍未验证的两条（两案共同的前置）

1. **上游风控是"按账号间隔"还是"按出口/IP 速率"计数？**（A 案删 gap 的前提；B 案列为阻塞性未知）
   —— 这同时决定"**per-IP 并发（asyncio M 通道）**"是否安全：若风控惩罚同 IP 并发，则 A 案的核心收益打折、
   应以"每 IP 单通道 + 多 IP"为主。
2. **多库原子提交与 WAL 的确切约束**（§3②）——决定三库分离的边界能不能划在"claim / 事件"之间。
