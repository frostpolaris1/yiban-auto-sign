# 本应设计成的程序逻辑：时间分块 × 多执行体（2026-09-22）

> 缘起：生产上出现 5 类问题（暂停号重复跳过、窗口内新号不入轮、手动冷却挡新号、手动签到跑在哪个执行体、
> 日志扇出）。本文把**现状是三层机制混在一起**这件事拆开，重新推导出"本应设计成"的分层逻辑与不变量，
> 并指出 5 个问题分别对应哪条不变量被破坏。
> 依据：`yiban/engine/schedule.py::build_schedule`／`_schedule_blocks`、`yiban/window.py::bounds`、
> `yiban/engine/round.py::run_queue_retry`、`yiban/engine/workers.py::run_fallback_worker`、
> `yiban/store/claims.py::try_claim`、`yiban/engine/state_io.py::need_second_run`、
> `docs/dev/cli.md:79,82`、`docs/dev/api-executors.md:96,106`，以及已移除的设计文档
> `docs/design-schedule-a.md`（commit `1141871` 的说明保留了核心口径）。

## 一、现状：三层机制混在一起

现在的实现把三件事写在同一条链路里，彼此没有明确契约：

| 层 | 现状承担 | 代码位置 | 混在一起的后果 |
|---|---|---|---|
| **时间层** | 错峰：把账号铺到窗口内的各时间点 | `schedule.build_schedule` → `{phone: 时刻}` | 只产出"计划"，但执行层拿到的是**账号列表**，于是"计划"退化成"排序提示" |
| **分工层** | 谁签哪个号：领取池先到先得 | `claims.try_claim`（唯一键 `phone+day`） | 计划与领取没有契约，"计划外账号"也能进队列（`round.py:294` 立即入堆） |
| **保障层** | 未了结的收敛：兜底常驻 + 补签轮 + 门禁 | `workers.run_fallback_worker`、`state_io.need_second_run`、`runner._day_off_skip` | 兜底在宿主未启用，"收敛"实际只剩一条又看不见新号的补签轮 |

**一句话诊断**：设计本是"**时间层决定何时、分工层决定谁、保障层负责收尾**"，实现却是"**执行层拿全量账号列表自己边排边领边跳**"——三层的职责没有落到接口上。

## 二、本应设计成的分层逻辑

### L1 时间层：产出"当轮可执行集合 + 每个账号的最早可执行时刻"

**输入**：账号集合快照、有效窗口、裁剪、块容量、用户自选片、order×dist。
**输出**（接口契约）：`plan = {phone: earliest_at}`，且**必须满足**：

- **L1-1 零占位**：暂停（`user_paused`）账号**不出现**在 `plan` 里（现状 `build_schedule` 已做到，但它不是唯一出口）。
- **L1-2 窗口有界**：所有时刻落在 `[eff_lo, eff_hi]`（`window.bounds` 的裁剪窗口）内；裁剪吃空窗口时回退默认窗口而不是产出空集。
- **L1-3 容量自洽**：`|plan| ≤ 块数 × 块容量`；超出走压缩模式并告警（间隔下限）。
- **L1-4 尊重自选**：自选片优先占位、片满先到先得、溢出就近顺延。
- **L1-5 可解释**：`pending`（"计划 HH:MM"）是**计划**不是结论——写进状态文件但**不算"已了结"**。

### L2 分工层：只回答"谁签"，且以"一天一次真实登录"为唯一硬约束

- **L2-1 领取即互斥**：`try_claim(phone, day, owner)` 是唯一入口，`UNIQUE(phone, day)` 保证一个账号一天只被一个执行体真实登录一次。
- **L2-2 动态分配，不预切分**：账号**不按执行体预先切分**，任何执行体可领任何"到点且未领"的账号（现状正是这么做的——这是多执行体特性的正确用法）。
- **L2-3 身份只在领取时确定**：owner = `worker-{slot}@{host}` / `fallback@{host}` / `single@{host}`（`api-executors.md:13`）；"哪个执行体做的"由 owner 决定，**不由谁被调用决定**。
- **L2-4 计划是准入条件**：执行层**只能执行 `plan` 里的账号**（外加显式 `--only` 目标）。计划外账号一律不入队——**这是现状最大的破口**（`round.py:294` 对计划外账号 `_push(_acc, _now0)` 立即入堆）。
- **L2-5 让位规则**：兜底/后续轮**不得抢全量轮正在执行的账号**（现状 `run_fallback_worker` 已有：`_run_lock_held()` → 让位，注释明写"否则会把全量轮的错峰计划与多执行体的分工一起冲掉"）。

### L3 保障层：负责把"未了结"收敛掉，且必须覆盖两类新增

- **L3-1 兜底 = 窗口内常驻补位**：`scripts/signin.py --fallback`（`cli.md:82`："窗口内反复接手未了结账号"）；**每轮 `load_accounts()` 重载**（`workers.py:257`）⇒ **窗口内新过审的号天然在覆盖内**；窗口关闭/周末门/暂停门自行退出；全量轮在跑时让位。
- **L3-2 补签轮 = 第二道网**：判据须为"**库里 active 账号 − 当日已有结论账号 > 0**"，而不是只遍历已有记录（`state_io.py:327-354` 现在只看已有记录 ⇒ 新号产生不了信号）。
- **L3-3 收敛定义**：每个账号每天**恰好一条终态结论**；`failed` 是终态（当日不再自动重试）；`pending` 不是结论；跳过类结论（窗口外/暂停/取消）**计入"当日已了结"**，避免每轮重复处理。现状缺的正是最后这条——`user_cancelled` 不在 `_CLAIM_DONE_STATUSES`（`round.py:75`）。
- **L3-4 门禁只在一处判定**：周末/暂停/窗口三门前移到派发之前（已做，`runner.py:225-231` 且豁免 `--only/--check-config/--probe`）。

### L4 手动通道：`--only` 是"即时单点"，走 L2/L3 之外的一条窄路

- **L4-1 即时**：设计口径是 `--only 即时`（`1141871`："按时间点排序执行（--only 即时）"）——**绕过分块计划，立即执行**。
- **L4-2 不可分派**：为单个（或少量）号码拉起 N 个执行体与"只签指定账号"（`cli.md:79`）自相矛盾 ⇒ `--only` 应**单进程执行**。**已对齐（派发拓扑已收敛）**：`runner.main` 在 `--only` 下直接走进程内单执行体路径，不再按执行体清单/`--workers` 派发监督进程（门豁免只覆盖门、不覆盖派发）；`--only` 的 rc 契约（含"仍能返回 3"）与三道门豁免不变。
- **L4-3 互斥靠领取池**：与在跑的全量轮互斥由 `try_claim` + 进程锁保证，**不需要**靠"参与多执行体派发"来互斥。
- **L4-4 完成判定看账号终态**：手动签到的"完成/未完成"必须以该账号的**当日结论**为准，**不能**以子进程退出码为准（退出码的"跳过(2)"含义里含"别的执行体领了"，那是成功不是失败）。

### L5 可观测：日志行数与账号数**线性且系数 ≈ 1**

- **L5-1 每账号一行结果**（成功/失败/跳过 + 原因）。
- **L5-2 每轮一个摘要块**（账号数、成功/失败/跳过、窗口、执行体分工）。
- **L5-3 内部状态进 DEBUG**（会话缓存作废、生成定位、缓存命中、剩余任务数）。
- **L5-4 通知按批次聚合**（一次"已发 N 封 → 收件人列表"），不按收件人逐行。

## 三、5 个问题 ↔ 被破坏的不变量

| # | 现象 | 被破坏的不变量 | 性质 |
|---|---|---|---|
| ① 暂停号被每个执行体争抢、重复跳过 | **L2-4**（计划外账号不该入队）+ **L3-3**（跳过类结论未计入"已了结"⇒不收敛） | 实现缺口：`runner.py:434` 传的是全量 `accounts`；`user_cancelled` 不在 `_CLAIM_DONE_STATUSES` |
| ② 窗口内新号不被自动签 | **L3-1**（兜底未启用）+ **L3-2**（补签判据看不见新号） | 部署缺口 + 判据缺口：机制在设计里**已有**，只是没跑 |
| ③ 手动冷却挡新号 | 设计缺口：**全仓无该键的设计记载**（L4 未定义冷却维度） | 需补设计：按账号短冷却 + 全局速率上限 |
| ④ 手动签到跑在哪个执行体 / "成功被报成未完成" | **L4-1/2/4**（应即时、单进程、按终态判定） | 实现缺口：派发判定不区分 `--only`；退出码 2 被判成"未完成" |
| ⑤ 日志扇出（每账号 5 行、冗余 89-93%） | **L5-1/2/3/4** | 实现缺口：内部状态与结果同层同级别输出 |

**结论**：**没有一条是"设计方向错了"**——都是"设计里的分层没落到接口上"或"设计已有一环没启用"。
唯一真正的**设计空白**是 ③（冷却维度），需要新增定义。

## 四、按分层重写后的运行图（应然）

```
             ┌─ L1 时间层 ────────────────────────────────────────────┐
窗口/裁剪/块容量/自选 → plan = {phone: earliest_at}（暂停号零占位）      │
             └───────────────────────┬───────────────────────────────┘
                                     │  plan 是"准入集合"
                    ┌────────────────┴────────────────┐
                    │                                 │
        ┌───────────▼───────────┐        ┌────────────▼─────────────┐
        │ L2 分工层（多执行体）  │        │ L4 手动通道（--only）     │
        │ 到点 → try_claim      │        │ 即时、单进程、同一领取池   │
        │ 先到先得，owner 记录   │        │ 完成看账号终态             │
        └───────────┬───────────┘        └────────────┬─────────────┘
                    │                                 │
                    └────────────┬────────────────────┘
                                 ▼
                    ┌─ L3 保障层 ─────────────────────────────┐
                    │ 兜底（窗口内常驻、每轮重载、让位全量轮）  │
                    │ 补签轮（判据 = active − 当日已有结论）    │
                    │ 收敛：每账号每天恰好一条终态结论          │
                    └─────────────────────────────────────────┘
```

**接口契约（三条）**：
1. **L1 → L2**：`plan` 是准入集合；执行层只跑 `plan` 内的账号（+ 显式 `--only`）。
2. **L2 ↔ L3**：未了结 = "active 且当日无终态结论"；由 L3 收敛；L2 不重复处理已收敛账号。
3. **L4 → L2**：`--only` 复用同一领取池与同一收敛口径，但**不参与多执行体派发**。

## 五、由此推出的改动清单（对应你已确认的口径）

| 项 | 改动 | 层 | 你已确认的口径 |
|---|---|---|---|
| ① | 执行入口按 `plan` 过滤（暂停号不入队）；统一补写一次 `user_cancelled` 并纳入"当日已了结" | L2-4 / L3-3 | 保留日历痕、不入池、`--only` 照签 |
| ② | 启用兜底（宿主常驻、窗口内、让位全量轮）**且**补签判据改差集 | L3-1 / L3-2 | 靠下一轮带上（机制待你核实：常驻兜底 vs 加晚轮） |
| ③ | 冷却改双轨：同号 60s + 全局速率上限（10 次/600s 可配） | L4（新增定义） | 同号 60s + 全局上限 |
| ④ | `--only` 不派发监督进程；完成判定以账号终态为准；退出码/文案区分"别人领了" | L4-1/2/4 | 都改 |
| ⑤ | 结果/摘要/内部三层分级；通知按批次聚合 | L5 | 方向待你定（实证已给 −69% 收益） |

**待你核实的仍是 §9 那三点**（②的落点机制、③的全局上限值、④的批量是否接受串行）；本文补第 4 点：
**L1-2 与 L3-2 之间有语义重叠**——若启用兜底，"补签轮判据要不要也放宽"就变成可选项（兜底已覆盖窗口内），
若两者都放宽，可能出现"同一账号被兜底与补签轮各跑一次"的重复（有 `try_claim` 兜底，安全但会多一次登录尝试）。
所以**建议二选一**：要么"兜底启用 + 补签判据不动"，要么"兜底不启用 + 补签判据放宽 + 加一条晚轮"。
