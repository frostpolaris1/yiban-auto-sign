# Python 脚本注释契约

面向仓库内所有 Python 脚本与模块。目标：任何人（包括初学者）能快速看懂并维护。注释是教学内容与维护线索，**不是任务报告**。

## 一、脚本头部注释（四问）

每个脚本/模块头部用简短注释回答：

1. **功能**：这个脚本是做什么的。
2. **归属**：它隶属于哪个更大的功能包/子系统。
3. **复用**：它有什么常用的、可被别处复用的东西（函数/常量/类）。
4. **通信**：它如何与外界交互——输入如何处理、结果如何输出、其他程序如何调用它、它调用了谁、谁调用了它。

## 二、函数级注释

- 按单个函数注释：做什么、基础原理是什么，如同向初学者讲课。
- 只对特别复杂的功能点或后期常维护的地方写；一眼能看出来的功能完全不写；不逐行解释。
- 注释解释「为什么/原理」，不复述「代码做了什么」。

## 三、旧注释瘦身

- 已有注释逐行检查废话，用 ponytail 准则精简（梯子第一问：这句话需要存在吗）。
- **清除任务痕迹**：审查轮次、批次编号、修复日期、「修掉了什么」式叙事——那是写给下一个阅读者的任务报告，不是注释。这类历史归 git 提交信息与 CHANGELOG。
- 必须保留：约束说明（为什么必须这样写）、外部契约（谁依赖这个行为）、踩坑警告。

## 四、精神

> 亲爱的 AI：当我让你修复某样东西时，我的意思是写下那三行修复它的代码。
> 而不是 400 行代码、17 个测试，以及一篇 12 页的文章，记录这个 bug 的最后日子。

修复就是修复，注释就是注释，两者都短。
