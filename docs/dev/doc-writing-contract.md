# 文档写作强制规范（三段式）

> **是什么**：`docs/` 下全部 Markdown 文档的强制结构契约——头部（检索层）/ 中部（详述层）/ 尾部（缺口层）三段式，与 `python-script-contract.md`（代码注释契约）对偶成双规范。
> **状态**：定稿（2026-09-23）
> **范围**：`docs/**` 的 .md 文档（设计/计划/审查/交接/报告/清单）。不覆盖 README.md、CHANGELOG.md、LICENSE、协议模板（部署者自填件）、代码注释（归注释契约管）。
> **读者**：一切产出文档的子代理与主控必读；M2/M3/M4 各文档写作者必读；交接提示词与工作流派单须把本文件列为必读项。
> **基线**：develop `b6457e6`

**关键词**：文档规范、三段式、文档契约、检索、目录契约、缺陷台账、待办、证据纪律、doc-writing-contract

## 速览（≤5 条结论）

- 所有文档强制三段：**头部（检索层）→ 中部（详述层）→ 尾部（缺口层）**，槽位固定、顺序固定。
- **头部自足**：只读头部即可回答三问——这是什么文档、结论是什么、有什么坑。
- **目录契约**：头部目录与正文标题 1:1 逐字一致；正文先写、头部后写。
- **尾部不许空**：明确缺陷与待办没有就写「无」；正文里的存疑必须在尾部有对应条目。
- 本规范**自举**：自身排布即第 6 节模板的实例。

## 1. 适用范围与效力

- **适用**：`docs/` 下所有 .md——设计文档、计划、审查报告、交接文稿、台账/清单、调研记录。
- **不适用**：README.md、CHANGELOG.md、LICENSE、用户协议/隐私政策模板（部署者自填件，格式另循旧例）；代码注释与 docstring 归 `python-script-contract.md`。
- **效力顺序**：用户决策 > 本规范 > 写作者行文偏好。两规范冲突时：代码内文本以注释契约为准，文档以本规范为准。
- **存量文档**：不一次性迁移；**下次编辑时轻量回改**（补头部两槽位与尾部两节即可，不重写正文）。
- **文件命名**（检索的一半靠文件名）：全小写连字符；点时性文档带日期后缀 `-YYYYMMDD.md`（如 `security-slim-plan-20260923.md`）；常青文档不带日期（如本文件）；同一主题迭代**覆盖同名文件**并在状态条注明取代关系，不堆积 `v2-final-final` 式文件名。

## 2. 头部（检索层）：五个固定槽位

头部 = 标题到目录为止的全部内容，**硬上限 45 行**，**不含证据细节、不含推理过程**。槽位顺序固定：

| 序 | 槽位 | 形态 | 规格 |
|----|------|------|------|
| 1 | **标题** | H1 | 「类型 + 主题（+ 日期）」一句话名词短语，如「万级调度算法设计方案」「生产日志巡检 · 缺陷清单」 |
| 2 | **身份条** | 引用块，五行固定字段 | 见下 |
| 3 | **关键词** | 一行 | 逗号分隔；必须含主题别名与缩写（例：调度、scheduler、10k），grep 一发即中 |
| 4 | **速览** | ≤5 个 bullet | 只写**结论**（是什么/得了什么结论/有什么坑），每条一行可读完 |
| 5 | **目录** | 编号列表 | 与正文 H2 **逐字一致**（见 §3 目录契约） |

**身份条五字段**（逐行、固定顺序、字段名照抄）：

```markdown
> **是什么**：一句话名词短语（本文档是什么，不是它包含什么）
> **状态**：草稿 | 定稿（日期） | 归档 | 已被 <文档名> 取代
> **范围**：覆盖 X、Y；不覆盖 Z（写明边界，防误引）
> **读者**：谁必读 / 谁选读 / 谁可略过
> **基线**：点时性事实的锚点（分支 + SHA 或日期）；常青文档写「常青」
```

**状态语义（强制）**：`草稿` = 不可作为决策依据；`定稿` = 可引用；`归档` = 历史事实，不反映现状；`已被 X 取代` = 一律改读 X。读者未在头部看到定稿状态的文档，不得被引为论据。

**头部验收判据**：合上正文只读头部，能回答三问——①这是什么文档？②结论是什么？③有什么坑/待办？答不出即不合格。

## 3. 中部（详述层）：目录契约与证据纪律

### 3.1 目录契约（承重规则）

- 正文 H2 的**编号与文字**与头部目录逐字相同；读目录跳转即所见即所得。
- **写序**：正文先成稿，头部目录最后抽取（防目录腐坏）。
- **增补**：定稿后加内容用子节 `N.M` 或末尾追加新编号 `N+1`，**禁止重排既有编号**（编号是稳定引用点，`§5.3` 类引用会被人当锚）。
- **删除**：删整节时目录该行改注「（已删，原 §N 主题）」留一期，下个版本再移除——防外部引用悬空。

### 3.2 节内排布

- 每个 H2/H3 开头**一句本节结论**，细节随后——扫读流只读各节首句也能拼出全文骨架。
- **可枚举事实用表格，论证用散文**；两者不混排充数。
- **单一事实源**：一个事实在全文只完整表述一次，他处用「见 §N」引用；重复表述是失真的温床。

### 3.3 证据纪律（与审查纪律同源）

- **代码事实**引用格式：`路径:符号`（主），行号可作补充但**必须标注基线**（`migrations.py:735 @b6457e6`）——行号会漂移，符号稳定；跨文件引用**禁用裸行号**（同注释契约）。
- **数字必须可复现**：给出产生它的命令（代码块）或写明统计口径。「约 5,000 行」这种估算要么给 `wc -l` 命令，要么明写「估算口径：……」。
- **「无 / 0 命中」类断言**：必须先证明检索模式有效（贴一个已知命中的对照输出），再贴 0 命中——防模式写错的假阴性。
- **外部来源**：URL + 取用日期；二手来源标注转引。
- **拿不准的不许当事实写**：宁可进尾部（§4），正文写「未验证」并指向尾部条目。

### 3.4 禁止项

- **任务痕迹**：批次号、工单号（T-XXX-N）、「修复轮/第 N 次/2026-09-23 改为」式叙事——历史归 git 提交信息与 CHANGELOG，文档只写结论态。
- **TBD 占位**：「待补充/TODO/略」一律不允许；未决事项进尾部待办。
- **复述型文本**：解释「代码做了什么」而非「为什么/约束/结论」的段落（教学性解释只在设计文档里允许，且服务于决策）。
- **明文敏感数据**：手机号/密钥/口令/凭据一律掩码形态（`138****0000`）；示例数据用假数据。

### 3.5 专属格式豁免

报告类一次性文档（如注释整备报告的六节结构）**中部**可使用其专属结构，但**头部五槽位与尾部两节不变**。专属格式的定义写在派单提示词里，二者以「头尾三层 + 中部专属」叠加适用。

## 4. 尾部（缺口层）：明确缺陷与待办

尾部 = 正文后固定两节（以分隔线 `---` 与正文隔开），顺序固定，**没有就写「无」**——空缺的显式声明是可信度的一部分，沉默的省略不是。

### 4.1 明确缺陷（本文档记录内容自身的）

**定义**：本文档**所记录内容**里的错漏——未验证的断言、自相矛盾处、与他文档的冲突、口径歧义。**不是**「被记录对象」的缺陷（那是正文/审查报告的正题，不要混入）。表格固定四列：

```markdown
## 明确缺陷
| 编号 | 缺陷 | 影响 | 处置 |
|------|------|------|------|
| D1 | …… | 引用本文档时会被什么误导 | 修正/标注/接受（写明动作与时机） |
```

### 4.2 待办

表格固定四列，**待办必须可执行**（有事项、有处置时点）；跨文档级的必修项引用 `must-fix-list.md` 的 `MF-N`，不在此重复展开：

```markdown
## 待办
| 编号 | 事项 | 处置时点 | 状态 |
|------|------|---------|------|
| T1 | …… | M3 动手前 / 条件触发时 | 未开始 / 进行中 / 已完成 |
```

### 4.3 尾部纪律

- **正文存疑 ⇔ 尾部有条**：正文出现「可能/大概/未验证/存疑」的每个断言，尾部必须有对应 D 或 T 条目；交付自检时双向核对。
- **缺陷条目也要可处置**：「影响」写清谁会被误导，「处置」写清动作与时机——只描述不处置的缺陷是抱怨，不是台账。
- 尾部条目编号在**本文档内**稳定（D1/T1 不复用），被外部引用后不得静默改义。

## 5. 写作流程与交付自检

**写序**：①中部成稿（含证据）→ ②尾部（收拢全部存疑与未决）→ ③头部（抽目录、提炼速览、补身份条）。

**交付前自检（六项，逐项过）**：

- [ ] 目录与正文 H2 逐字对照一遍（编号 + 文字）；
- [ ] 合上正文只读头部，三问（什么文档/什么结论/什么坑）能答；
- [ ] 全文数字都有命令或口径；
- [ ] 「无 / 0 命中」断言都有对照证明；
- [ ] 正文存疑句与尾部条目双向核对完毕；
- [ ] 敏感数据抽查（手机号/密钥/口令）全为掩码。

**强制落地方式**：①交接提示词与工作流派单把本文件列为必读；②审查子代理的检查项含「产出文档是否合本规范」；③文档评审不合格即退改，与代码评审同权。
