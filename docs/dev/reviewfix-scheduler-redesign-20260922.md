# 调度算法重设计：单窗口连续调度器（CWS）—— 2026-09-22

> 视角：**算法设计**（不考虑改动工作量）。目标：在"一个窗口内把 N 个账号各真实登录一次"这个约束下，
> 同时满足 ①服务端安全（聚合速率可控且可自适应）②人类相似度（到达分布）③用户自选时段（硬约束）
> ④恰好一次与收敛（多执行体）⑤中途来号/暂停/失败重试。
> 基准数据（生产实测）：有效窗口 `W=4470s`（窗口 06:30–07:50、前裁 30s、后裁 300s）、`N=61`、
> **29/61 有自选片**、`avg≈1.87s`（拟真）/`3s`（配置缺省）、`gap=10s`、块 5 分钟 × `block_cap=15`、
> 单执行体容量实测 344~390、当前 `M=2`。

---

## 一、现状算法的三条结构性缺陷（不是 bug，是模型问题）

**缺陷 A：把"节奏"写成了"每执行体的间隔"，于是容量与执行体数耦合错了。**
现状容量模型 `capacity = (W − avg)/(avg + gap) + 1`（`schedule.capacity_accounts`），含义是
"**一个执行体串行服务、每个账号之间留 gap**"。生产 `avg=1.87, gap=10` 得 `(4470−1.87)/11.87 ≈ 377 ~ 390`
（与实测一致）。但"gap"原本混了两件事：**服务端安全间隔**与**人类相似度间隔**。
一旦要 5000 账号，现状模型给出"需要 13~15 个执行体"，而**服务端看到的聚合请求速率在两种方案下完全相同**——
多出来的执行体只是在补偿被写死的 gap，不是在提高真实吞吐。

**缺陷 B：没有"聚合速率"这个一等公民，安全上限随 M 线性放大。**
每执行体各自按 `avg+gap` 与 `MIN_EXEC_GAP/EXEC_GAP_MIN` 自我节流；"已过点立即"、迟到开轮、失败重试
都会让某个执行体瞬时连发，而**没有任何机制约束 M 个执行体的合计速率**。M=20 时，理论合计速率是无治理的
`M/avg`，与"安全"这件事脱钩。

**缺陷 C：计划是快照、不是准入集合，于是"收敛"要靠三套并行机制兜。**
`runner.py:246` 一次快照 → 轮内新号不可见（问题②）；计划只当排序提示，计划外账号被 `round.py:294` 立即入堆
（问题①的根）；暂停号"跳过但不收敛"导致每轮复读；失败的收敛分别由"补签轮判据""兜底常驻""下次轮"三条路各管一段，
每条都带自己的门与判据——于是产生 ①⑤ 这一类"行为对、但代价与噪声都错"的现象。

## 二、新模型：把窗口当成一个"受速率约束的截止期调度问题"

### 2.1 形式化

| 符号 | 含义 |
|---|---|
| `W = [t0, t1]` | 有效窗口（`window.bounds` 的裁剪结果） |
| `A(t)` | **派生**工作集：`{a : a 生效(非删除/已过审) ∧ ¬user_paused ∧ 今日无终态结论}` —— 每轮循环**重算**，不缓存快照 |
| `r_a` | 释放时刻（**不是** deadline）：自选片 → 片区间内的确定性抖动；否则 → 按目标密度 `φ` 的逆 CDF 采样 |
| `d_a` | 软截止：`min(自选片区间末, t1 − 重试储备)` —— 决定重试优先与可行性 |
| `λ_plan(t)` | 计划到达速率（号/秒），由 `N` 与"窗口扣掉重试储备"决定 |
| `Λ(t)` | **安全天花板**（号/秒），在线自适应，与 M 无关 |
| `S(·)` | 单账号服务时间分布（在线测：EWMA + p95），替代写死的 `avg/gap` |
| `M` | 并行执行体数（并发度），**只决定"能不能跑得动 λ"，不决定 λ 本身** |

**唯一硬约束**：`λ_actual ≤ min(λ_plan, Λ)`。**目标函数**：在 `t1` 前完成 `A(t1)`，且到达分布符合 `φ`（人类相似度），
自选片为硬约束。

### 2.2 四个核心机制

#### 机制 1：派生工作集（消灭"计划外/快照"这一整类问题）
调度器不再持有"账号列表快照"，而是每轮循环从状态派生：
`A(t) = 生效账号 − 今日终态账号`。于是
- 中途过审的新号**自动进入**（无需兜底、无需补签轮、无需部署开关）；
- 暂停/删除**自动退出**（零 claim、零跳过、零日志）；
- "计划外账号立即入堆"这种 bug 在结构上不存在（不在 `A(t)` 里就没有堆位）。

#### 机制 2：逆 CDF 密度整形 + 自选片作为区间硬约束
- 目标密度 `φ(t)`：沿用现有 `uniform` / `normal` 两种形态，但**直接以"号/秒"表达**，取代"5 分钟块 × 块容量"——
  消除块边界量化（块内等分 + 抖动本质是在用离散近似连续密度）。
- 每账号的目标时刻 **不落库、不写计划表**：`r_a = Λ⁻¹(u_a)`，`u_a = H(phone, day) ∈ [0,1)`（`sequence` 用稳定 hash，
  `random` 用当天种子）。**确定性、可复现、可审计**（日志里带上种子即可重放当天分布）。
- **自选片升级为区间**：片是 `[s, s+Δ)` 而不是一个点，片内再做逆 CDF 抖动 ⇒ 既满足"我选了 07:00 这一格"，
  又不把同格的人叠成一束。
- **热点水位填充（water-filling）**：自选片是先占的硬约束；剩余质量在"未被占用的时间轴"上重新归一化，
  让**瞬时速率**尽量平坦（现状"片满先到先得 + 溢出就近顺延"只保证不超容，不保证速率平坦）。
  生产 29/61 有自选片，这一条直接决定实际形状。

#### 机制 3：全局 GCRA 速率治理 + AIMD 自适应（把"安全"从配置里拿出来）
- **GCRA（Generic Cell Rate Algorithm）**：一个**跨执行体共享**的令牌源（状态 = `TAT`，理论到达时间）。
  每次发请求前：`if now ≥ TAT − B then TAT = max(TAT, now) + 1/λ`，`B` 为突发容限（≈ M，允许 M 个执行体同时开工）。
  O(1)、无需锁队列、天然支持**变速率** `λ(t)`——这正是"密度随时间变化"的调度需要的。
- **`λ(t) = min(λ_plan(t), Λ)`**：前者是人类相似度与截止期，后者是安全。
- **`Λ` 在线自适应（AIMD）**：成功连续 → 小幅上探（`×(1+α)`，上限 `Λ_hi`）；出现拥塞信号（429/5xx/超时/
  p95 超阈/被拦页）→ 乘性回退（`×β`，下限 `Λ_lo`）并冻结一个短窗。
  ⇒ **取代手工标定**：现在"capacity_probe 实测 390/建议 260"是人工标定的常量，新模型把它变成运行时观测量，
  同时也正好产出项目一直想要的"容量拟合"数据。
- 关键性质：**聚合上限与 M 无关**。M 只影响"能否把 `λ` 兑现成实际吞吐"，不影响服务端看到的速率上限。

#### 机制 4：期限感知的重试 + 可行性预测
- 释放时刻 `r_a` 与软截止 `d_a` 分离：`r_a` 管人类相似度，`d_a = t1 − 重试储备` 管**必须赶在窗口关前收尾**。
  重试落点取 `min(backoff 采样, d_a − 剩余尝试所需时间)`，**绝不再出现"重试抽样落到窗口外 → 静默跳过"**
  （这正是 T-WIN-1 那一类 53 分钟口径分裂的来源）。
- **可行性预测**：任意时刻用 `|A(t)|`、`S(·)`、`M`、`Λ` 投影完成时刻 `t̂`：
  `t̂ > t1` ⇒ 分级响应：①先把 `φ` 压平（换取速率）②再把 `λ` 顶到 `Λ_hi` ③仍不行则**显式申报缺口**
  （"预计缺 k 个账号签不完，建议加宽窗口/降低规模"），而不是静默跳过。

#### 机制 5（跨层）：终态单写 + fencing —— 收敛由构造保证
每 `(账号, 日)` **恰好一条终态**（success/already/no_task/failed/no_position/skipped_window/user_cancelled/paused），
写入带**单调 epoch（fencing token）**：过期执行体的写被拒。于是
- 工作集收缩是自动的（跳过类也是终态）⇒ ①的"每轮复读"消失；
- 时钟回拨/陈旧写覆盖（T-CLAIMS-3）在结构上被挡住。

## 三、伪代码

```python
# ── 调度器（窗口内常驻；cron 只在窗口开启时拉起，窗口关闭自行退出） ────────────
def run_window(W, M, cfg):
    gov = GCRA(lam=lambda t: min(lam_plan(t, work_set(W, t)), lam_max.cur), burst=M)
    while clock.now() < W.t1 and work_set(W) :                 # 派生工作集，每轮重算
        if congestion_signal():                                # 429/5xx/超时/p95↑/被拦页
            lam_max.retreat(); gov.freeze(short)
        else:
            lam_max.probe_up()                                 # AIMD 上探（有上下限）
        ready = [a for a in work_set(W)
                 if release_time(a) <= clock.now() + lead]     # lead=允许小幅提前（工作守恒）
        ready.sort(key=lambda a: (pref_deadline(a), d_a(a), u_a(a)))   # 期限优先 + 确定性
        for a in ready:
            if not gov.acquire(): break                        # 速率未放行 → 本轮回 worker
            if not claims.try_claim(a, day, owner, epoch):     # fencing 领取
                settle(a, TERMINAL_DELEGATED); continue
            t_start = monotonic()
            ok, status = attempt_signin(a)
            service_est.observe(monotonic() - t_start)         # 在线学 S(·)
            settle(a, terminal_of(status), epoch)              # 终态单写
        gov.publish_metrics()                                  # 计划 vs 实际、λ、队列深、滞后、S(·)
    forecast_and_alarm_if_short(W)                             # 可行性预测 → 显式缺口告警
```

## 四、与现状的量化对比（用生产真参数）

| 维度 | 现状 | CWS | 差异来源 |
|---|---|---|---|
| 执行体需求（N=5000, W=4470s） | **13~15 个** | **约 4 个**（λ=1.29 号/s × avg 1.87s ÷ 0.75 利用率） | 现状把 `avg+gap` 当串行周期（`(1.87+10)/1.87 = 6.3×`）；CWS 的 gap 折进全局速率，执行体只提供并发 |
| 服务端看到的聚合速率 | 无显式上限，M 线性放大 | `λ(t) ≤ min(λ_plan, Λ)`，**与 M 无关** | 机制 3（GCRA + AIMD） |
| 达到速率上限时的正确动作 | 无模型，只能发现"慢" | 加执行体无用（瓶颈是速率）→ 加宽窗口或申报缺口 | 机制 4（可行性预测） |
| N=61 的分布 | 3 号/分（`block_cap 15 / 5 分`），22 分钟跑完、余 55 分钟空 | `λ_plan = 61/(4470−600) ≈ 1 号/64s`，**铺满到留 10 分钟重试尾巴** | 机制 2（密度按"窗口 − 重试储备"定，而不是按块容量） |
| 中途来号 | 需兜底/补签轮，宿主上还没启用 | 工作集派生 ⇒ 立即纳入 | 机制 1 |
| 暂停号 | 每个执行体跳一次、每轮复读 | 不在工作集 ⇒ 零动作（仅留一条终态日历痕） | 机制 1 + 5 |
| 重试 | 抽样可能落窗口外 → 静默跳过 | 落点有界于 `d_a`，绝不越过窗口 | 机制 4 |
| 容量标定 | 人工（capacity_probe 实测 390/建议 260） | 在线估计 `S(·)` 与 `Λ`，标定数据成为副产品 | 机制 3 |
| 轮次结构 | 首轮 + 补签轮 + 兜底（三套门/判据） | **一个窗口一个常驻调度器**（cron 只负责拉起、关闭自退） | 机制 1+5 |

**核心结论**：现状把"**服务端安全间隔**"与"**每执行体串行节奏**"合并成同一个 `gap` 常量，导致
①执行体需求被高估约 **6×**（`(avg+gap)/avg`）②聚合速率无上限、随 M 放大 ③窗口利用率靠"块容量"这一离散近似。
CWS 把三者拆开：**密度（人类相似度）／速率上限（安全，自适应）／并发度（执行体）**，各管一件事。

## 五、不变量（新设计的验收口径）

1. **I-速率**：任意 1 秒窗内实际请求数 ≤ `min(λ_plan, Λ)` 的积分 + `B`（突发容限）；且与 M 无关。
2. **I-分布**：给定 `(date, seed)`，未选片账号的到达时刻可**逐号重放**；自选片 100% 落在其区间内。
3. **I-收敛**：每个生效账号当日恰好一条终态；工作集单调收缩至空；跳过类算终态。
4. **I-恰好一次**：`(phone, day)` 唯一领取 + fencing epoch ⇒ 任意 M、任意时钟跳变下都不重复真实登录。
5. **I-截止**：所有尝试（含重试）落在 `W` 内；做不到时**显式申报缺口**，不静默跳过。
6. **I-可观测**：每账号 1 行结果 + 每窗口 1 个摘要 + 一条指标时序（λ、Λ、队列深、滞后、S(·) 分位）。

## 六、风险与失效模式（新设计引入的）

| 风险 | 缓解 |
|---|---|
| 共享 GCRA 状态是新的协调点（DB 行/CAS） | 拿不到令牌源时**降级**为"每执行体本地 GCRA + 全局静态上限"；宁可慢，不可失控 |
| AIMD 上探可能触及风控 | 上探步长与 `Λ_hi` 由运维给定上界；拥塞信号一票乘性回退；默认关闭自适应（只保留静态 λ） |
| 密度按"窗口 − 重试储备"定 ⇒ 首次尝试整体偏晚 | 重试储备独立可配；小 N 时可把储备压到 0 让分布更前（保留现状 `block_cap` 作为"最小密度地板"等价物） |
| 自选片由"点"变"区间" ⇒ UI 语义微调 | 显示仍按原片；只是内部多了一个片内自由度（对外不可见） |
| 全局速率上限意味着"加执行体不再提吞吐" | 这正是要显式化的认知：容量 = `W × Λ`；UI/文档要把口径从"每执行体账号数"改为"窗口速率 × 窗口长" |

## 七、落地分阶（仅作风险控制提示，不涉及工作量评估）

1. **先取"聚合速率"这个一等公民**（GCRA + 静态 `Λ`），把 `gap` 折进 `λ` —— 这一步就能拿到"执行体需求 ÷6"的收益，且不改任何对外行为。
2. **再把计划改成派生工作集**——①（暂停复读）、②（新号入轮）在结构上消失，补签轮/兜底从"必需"降级为"可选保险"。
3. **最后开自适应（AIMD）与可行性预测**——容量标定从人工常量变成运行时观测 + 显式缺口告警。
4. 日志三层（结果/摘要/指标）随第 2 步一起做，因为指标本来就是调度器的输出。

## 八、专项：多执行体 + fallback 强制开启后，还需要补签轮吗？

**先摆事实（来自代码，不是按名字推断）**：

| 机制 | 进程形态 | 覆盖方式 | 吞吐 | 起跑时点 | 与对方的关系 |
|---|---|---|---|---|---|
| 补签轮（07:12 / 容器 07:10） | **多执行体并行**（走 `run_worker_supervisor`） | 一次性整轮 | 与首轮同量级：`M × 单执行体容量(344~390)` | 窗口已进行 42 分钟 | 触发时持有全局轮锁，**兜底会让位** |
| fallback（`scripts/yiban-fallback.sh`） | **单进程常驻**（`run_fallback_worker`，一次只处理一个账号；有独立锁 `signin-run.lock.fallback`） | 窗口内每 60s 扫一遍（有活干时 5s） | `1/avg` ≈ **0.33~0.53 号/s** → 整窗（4470s）最多 ≈ **1490 号**（avg=3） | 设计上**窗口开启时**由 cron 拉起（生产未启用） | 全量轮在跑时**让位**（`_run_lock_held()`） |

**结论：分两种情形，答案相反。**

### 情形一：保持现状架构（fallback 仍是单进程）→ **仍需要补签轮**

两者是**互补**，不是冗余：
- fallback 是"**低强度、连续、单进程**"的捡漏：适合零星漏签（今天生产那种 3 个号的尾巴，115 秒就收掉）。
- 补签轮是"**高强度、一次、并行**"的恢复：首轮被 run.sh 的 timeout（生产 `签到超时: 5039s`）击杀、或成规模失败时，
  只有多执行体并行能在窗口内收完。**单进程 fallback 在数量级上做不到**（5000 号需 2.6 小时 ≫ 74.5 分钟窗口；
  即便 1500 号也刚好占满整个窗口、没有任何重试余量）。

⇒ 所以"强制开启 fallback"**不能替代补签轮**，它只能降低补签轮被触发的频率（大多数日子会判"无需补跑"）。

### 情形二：把 fallback 升级为"窗口内多执行体常驻调度器"（= 本文的 CWS）→ **不需要补签轮**

此时"第二轮"这个概念本身消失：调度器从窗口开启持续跑到关闭，工作集派生、M 个执行体持续服务未终态账号。
补签轮的三个职责被吸收，且**每一项都做得更好**：

| 补签轮的职责 | CWS 里由谁承担 | 为什么更好 |
|---|---|---|
| 捉漏（未了结账号） | 连续工作集 | 60s 级响应 vs 固定 07:12 一次；不会"差一点就错过" |
| 首轮未收尾/进程崩了 | 守护重启（systemd/cron 拉起常驻进程） | 恢复粒度为"秒"而不是"等下一个 cron 点"；不消耗一整个并行轮次 |
| 当日收尾/标记 | 调度器窗口关闭时写一次 | 单一写入者，无"哪一轮是最后一轮"的歧义 |

### 补签轮的固有缺陷（佐证"再跑一整轮"不是好机制）

它的计划是**按整窗（06:30–07:50）生成的**，但它 07:12 才起跑 ⇒ `build_schedule` 产出的时刻大部分已过去，
`round.py:294` 对"已过点"账号一律 `_push(_acc, _now0)` **立即入堆** ⇒ 补签轮本质是**一次突发**：
错峰、人类相似度、块容量这些属性在它身上**本就不成立**（只剩"尽快收完"）。也就是说，
补签轮是"用正确机制的错误实例"来做恢复——而 CWS 的连续模型根本不会遇到"窗口已经过了 42 分钟才重新规划"这件事。

### 取消补签轮会牵动的四个契约（这一条比"要不要取消"本身更重要）

1. **`need_second_run` 的消费者消失**：`state_io.need_second_run` = `not full_run_done_today ∨ has_undone_accounts_today`——
   它是"当日是否收尾"的唯一判据，现在只有 run.sh/容器调度器在用它决定补跑。取消补签轮后，这个判断要么迁移给调度器收尾，要么删除（否则成死代码）。
2. **`run.sh` 退出码 10 与 `docs/dev/cli.md §3`**：`10 = 需要补跑` 是"仅该子命令使用"的对外契约，取消后要同步文档与测试。
3. **`_is_second_run` 告警口径**：`_maybe_alert_zero_success` 等用"是否补签轮"选择措辞/是否告警；需要一个替代信号
   （例如改成"窗口内最后一次尝试之后"）。
4. **发布门禁的"有效轮次"定义**（PROMPT.md §6.10）**直接依赖 `run.sh` 完整执行 + 退出码 0**。
   一旦变成"一个窗口一个常驻进程"，"轮次"这个概念需要重新定义——**这会影响 main 分支的推送门槛**，
   属于必须与用户确认的治理性变更，不能顺手改。

### 建议

- **短期（现状架构不变）**：把 fallback 按它的设计用法在**窗口开启时**拉起（`5 6 * * * ... yiban-fallback.sh`，开关打开），
  补签轮**保留但降级为恢复手段**（不再是日常路径）；同时修 `need_second_run` 让它能看见窗口内新号
  （这样"补签轮"在需要时真的能收新号，而不是判"无需补跑"）。
- **长期（走 CWS）**：取消补签轮，把上面四个契约作为一次性迁移项做掉（尤其第 4 条要先拿到用户对门禁定义的确认）。
